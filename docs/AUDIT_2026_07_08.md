# P42 Prizes — Full-Protocol Security & Mechanism Audit

**Date:** 2026-07-08  
**Method:** multi-agent audit (10 dimensions, Fable 5 finders) → independent adversarial verification of every finding → lead-auditor synthesis. Managed by Opus 4.8; the top findings were independently re-verified against the source by the orchestrator before publication.  
**Scope:** all 7 Solidity contracts, the Python gate library (~4.3k LOC), all 10 math verifiers, the agent clients (solver/operator/indexer/DA), schemas, deployment scripts, and the gate documentation.

**Result:** 45 findings raised, **38 confirmed** through adversarial verification (4 high, 7 medium, 21 low, 1 info); 7 plausible findings were **refuted** and are listed in the appendix.

> **Remediation status (2026-07-09).** This document is the frozen audit record; code-level descriptions below reflect the pre-remediation HEAD. The headline F1 finding (seed-relative scoring, no on-chain frontier) has since been remediated: the contracts now track a monotone per-problem `bestScoreAtoms` and credit each finalize with the marginal `Δ_i = prev_best − new_score`, so shares are `Δ_i/ΣΔ_j`, and seeding moved to the autonomous open-witness-phase design ([`OPEN_WITNESS_SEEDING.md`](OPEN_WITNESS_SEEDING.md)). Additional findings were remediated in the follow-up `Audit F*` commits (see `git log --oneline --grep="Audit F"`).

> **No real ETH is at risk at the current testnet phase.** Severities are calibrated to the testnet phase with the Gate-2 blockers open; items marked High are *must-fix-before-real-ETH*, not funds-at-risk-now. The on-chain fund-custody core is defensively sound — the strongest fund-theft exploit attempts were investigated and refuted (see appendix).

## Executive summary

P42 Prizes is a well-structured testnet-phase protocol whose on-chain settlement core is largely sound, but whose core economic mechanism has a genuine, must-fix-before-funding soundness hole and whose off-chain enforcement/evidence layer is not yet production-hardened. Across all audit dimensions, 33 distinct issues survived adversarial verification (4 high, 7 medium, 21 low, 1 info). The single most important theme is that "valid" does not imply "a real improvement": every verifier scores improvement as an absolute distance from a static per-problem seed constant, and neither reveal/finalize nor the payout ledger tracks a live frontier best-score — so the protocol's advertised Delta_i/SigmaDelta_j payout equation is not actually implemented. This lets a late free-rider extract the majority of a pool for a marginal step, pays false prizes for solutions strictly worse than the already-public baseline (hadamard-668), and (in signed-autoconvolution-c3) certifies a wrong functional — all unchallengeable because a re-run reproduces the same wrong value. The second theme is that the permissionless bonded-challenger channel is thin and cheaply neutralized (free self-challenge burns the one-shot slot; the sole automated operator silently drops retry submissions, crash-loops on public RPCs, and declines the largest frauds), so enforcement currently rests entirely on the single trusted Phase-1 resolver the project itself flags as its core trust concession. Notably, several plausible high/critical contract exploits (unbounded-atoms overflow-brick, bond-inflation censorship, over-collateralized commit bond, minImprovementAtoms bypass) were investigated and correctly refuted — the contracts fail closed in most edge cases. No real ETH is at risk today; every high/critical-on-mainnet item is correctly held lower by the testnet phase and explicit open Gate-2 blockers.

## Overall posture

Sound scaffold, unsound mechanism. The Solidity settlement layer (bond lifecycle, commit/reveal/finalize/claim, escrow accounting, overflow safety, timelock structure) is defensively written and survived the strongest fund-theft exploit attempts, so the dominant risk is NOT contract fund-theft. The dominant risk class is mechanism soundness: the payout formula the whole protocol sells is computed against a fixed seed with no on-chain frontier, so verified "progress" can be paid for non-progress or over-credited, and the two math-verifier soundness bugs (seed-relative scoring / trivial hadamard-668 seed, and the C3 signed-max vs L-infinity error) produce reproducible-yet-wrong certificates that in-protocol challenges cannot defeat. A close-second class is the thinness of the enforcement-and-evidence layer around the contracts — a free self-challenge neutralizes the permissionless dispute channel, the lone automated operator has three independent ways to silently stop policing, and the gate documentation/reconciliation/red-team evidence has drifted ahead of the DA-refactored code (the BaseScan-verified deployment predates the refactor; reconcile silently under-reports; "audited"/"trustless"/"independent" wording contradicts the repo's own Gate-2 blockers). None of this endangers real funds at the current testnet phase, and the project's own gate ledger honestly tracks most (not all) of these as open. Before any real-ETH funding, the frontier-tracking redesign and the two verifier fixes are non-negotiable, the challenge channel must survive a Sybil, and the gate evidence must be regenerated against the deployed bytecode.

## Systemic themes

- Valid does not imply real improvement — no live frontier. Every verifier scores improvement as an absolute distance from a static seed constant, and reveal/finalize/recordCredit never track a monotone per-problem best-score, so the advertised Delta_i/SigmaDelta_j payout is not implemented: false prizes (hadamard-668 trivial seed), double-counting by late free-riders, self-laddering, a wrong functional (C3 signed-max), and atom quantization coarser than the validity threshold all live here (ranks 1, 2, 6). This is the protocol's core value proposition and the class that most needs a redesign before funding.
- The permissionless enforcement channel is thin and cheaply neutralized. A free self-challenge burns the one-shot challenge slot; the sole automated operator has three independent silent-failure modes (drops retry submissions, crash-loops on public RPC, declines the largest frauds); and expireRevealed can strip an honest challenge-winner's bond. Fraud detection therefore rests almost entirely on the single trusted Phase-1 resolver — exactly the trust concession the project flags as its hard real-ETH blocker (ranks 3, 4, 5, 8, 13).
- Off-chain agent/runner tooling is not production-hardened. No lease reaper, unchunked getLogs, predictable-/tmp writes, path traversal, mutable image tags, unpinned base image / pip, self-attested host matrix, non-canonical-report status inversion, and collision-prone transcript names. Individually low, collectively they mean the evidence-and-policing layer wrapped around the (relatively solid) contracts is the fragile part of the system (ranks 7, 8, 14, 19, 20, 21, 24, 25, 26, 33).
- Gate/evidence documentation has drifted ahead of the DA-refactored code and overclaims. The BaseScan-verified canonical deployment predates the DA refactor; reconciliation now silently under-reports; the adversarial-campaign/red-team matrix attests a removed permanence gate; and 'audited'/'independent'/'trustless' wording contradicts the repo's own Gate-2 blockers. Because the gate ledger IS the project's trust artifact, honesty drift here is a first-class risk even though no funds move from gate status (ranks 9, 10, 11, 28, 31, 32).
- Determinism and reproducibility are asserted but not enforced at the executing layer. PYTHONHASHSEED/thread caps advertised but never set; sandbox accepts mutable tags; images built from a mutable base with unpinned pip; deploy script cannot even produce the documented off-chain-DA mode. Determinism is currently a property of author discipline plus the (forgeable) admission N-host matrix, not of the runner (ranks 19, 20, 21, 23, 27).
- Positive note: the on-chain fund-custody core is defensively sound. The strongest fund-theft exploit attempts were investigated and correctly refuted (unbounded-atoms overflow-brick, bond-inflation censorship, over-collateralized commit bond, minImprovementAtoms bypass, GraphQL/JSON-parse crashes, opaque evidence anchors). The contracts generally fail closed; the residual on-chain findings are DoS/griefing and governance-liveness, not theft.

## Findings (ranked)

### 1. [HIGH] Improvement is scored against a static per-problem seed, not the live frontier; the ledger never tracks a best score (incl. hadamard-668 trivial seed)
- **Category:** math-soundness
- **Location:** `contracts/src/P42PayoutLedger.sol:90 (+ problems/hadamard-668-defect/verifier/verify.py:20, all 10 verifiers)`
- **Impact:** The core payout equation Delta_i/SigmaDelta_j is not implemented. Every verifier computes improvement as an absolute distance from a hardcoded seed constant, recordCredit merely sums atoms (creditAtomsOf[solver]+=atoms; totalCreditAtoms+=atoms) with no monotone frontier or seed->optimum cap, and reveal only checks improvementAtoms>0. Three reproducible-thus-unchallengeable breaks: (a) a late free-rider who reads an honest solver's on-chain-DA'd solution and takes one marginal step is credited its full seed-relative distance and captures the majority of the pool (hadamard-mini: ~54.5% for a true 1/6 marginal); (b) hadamard-668's SEED_BEST is the trivial all-pairs count 222778, so a matrix strictly WORSE than the bundled Sylvester baseline (defect 55444) certifies valid with a large positive improvement — a false prize for a non-improvement (edges-vs-triangles has the same defect with a constructible worse-than-public instance); (c) a single solver ladders (defect 3 then 0) to inflate its own denominator share. The operator's fraud predicate uses the same seed-relative value, so none is challengeable.
- **Fix:** Track a monotone per-problem frontier best-score on-chain (claimedScoreAtoms is already carried through reveal but unused); at finalize require the new score to strictly beat the stored best by >= min_improvement and credit only (prev_best - new_best). Set each problem's seed_best to the true best-known score (mirror erdos-min-overlap, which correctly pins the published Haugland record). Have the verifier take the current best as input and reject Delta<=0.

### 2. [HIGH] signed-autoconvolution-c3 verifier scores with signed max(c_p) instead of the reference L-infinity norm max|c_p|
- **Category:** math-soundness
- **Location:** `problems/signed-autoconvolution-c3-upper/verifier/verify.py:129`
- **Impact:** score = 2N*max(coefficients)/total^2, guarded only by max_coefficient<=0. The certified functional is max_p |c_p|. Since sum(c)=total^2>0 forces max(c)>0, max|c| >= max(c) always, so the verifier can only UNDER-report the minimized score and OVER-report improvement = max(0, 3/2 - score). A negative-dominant construction (reproduced: max(c)=5 but min(c)=-8, so true L-infinity uses 8) certifies valid=true with a positive improvement while the true functional value may be >= 3/2 (no real improvement). Challengers re-run the same pinned verifier and reproduce the same wrong value, so the false certificate is unchallengeable in-protocol; under Delta_i/SigmaDelta_j the over-credit siphons pool share. SPEC.md's 'the dropped outer absolute value is inert' holds only for the one bundled positive-dominant witness and would plausibly survive gate review.
- **Fix:** linf = max(max(coefficients), -min(coefficients)); score = Fraction(2*N*linf, total*total). Keep argmax reporting for the max-magnitude coefficient. Do not rely on a positive-dominance precondition unless you also hard-reject any submission where -min(coefficients) > max(coefficients).

### 3. [HIGH] A submission can be challenged only once ever; a free self-/Sybil-challenge burns the slot and immunizes fraud
- **Category:** economic
- **Location:** `contracts/src/P42ChallengeManager.sol:172`
- **Impact:** challenge() reverts P42_ALREADY_CHALLENGED whenever challenges[submissionId].challenger != address(0), the record is never cleared (not by resolve at 217, not by expireChallenge at 265), and there is no challenger != solver guard. A fraudulent solver self-challenges from a sock-puppet in the reveal block (status->Challenged), blocking every honest challenger for the whole 72h window; after the window the solver front-runs expireChallenge (sock-puppet's counter-bond refunded in full, line 268) and finalizes. On a genuine honest challenge the solver's forfeited posting bond routes to the challenger (line 237) — self-challenging returns both bonds to the attacker, eliminating even the posting-bond forfeiture deterrent. Net cost: gas + a refundable 72h capital lock. This neutralizes the entire permissionless bonded-challenger channel; only the trusted Phase-1 resolver (who can still rule challengerWins on the live Sybil challenge within the window) remains. Would be critical in trust-minimized Phase 3.
- **Fix:** Add a challenger != solver guard (and disallow a challenge bond sourced from the solver). Key challenges by an incrementing id or by (submissionId, challenger) so a frivolous slot cannot lock out others; on a solver-favorable expiry/resolution, re-open the submission to fresh challenges for the remaining/renewed window. Cap cumulative added window time instead of making the first challenge a permanent one-shot lock.

### 4. [HIGH] Operator advances fromBlock unconditionally, permanently dropping every 'leave for retry' submission
- **Category:** dos
- **Location:** `agent/operator.mjs:168`
- **Impact:** scanOnce sets fromBlock = latest+1 at the end of every pass, but seven branches continue WITHOUT seen.add on an explicit retry promise (tx not yet retrievable, calldata undecodable, off-chain reveal with no store, Arweave miss, local blob missing, sha256 anchor mismatch). The next window starts past those blocks, so they are never re-queried — the retry structurally never happens for the daemon's lifetime. A fraudulent off-chain-DA solver reveals, withholds the blob through the operator's next ~12s scan (DA MISS -> continue -> cursor jumps past the reveal block), then posts bytes late or never; the operator never re-verifies and never challenges, and finalize() has no DA-availability precondition (permanenceHash unchecked), so the invalid/inflated claim finalizes after 72h. The operator is the sole automated challenger (the indexer is read-only). Also drops any on-chain-DA submission that hit a one-off RPC hiccup. Process restart within 72h recovers, but nothing enforces one and daemon mode is primary.
- **Fix:** Do not advance the cursor past unresolved events. Track the lowest block of any submission left for retry this pass and set fromBlock = min(latest+1, lowestPendingBlock), or keep a persistent per-submissionId state machine independent of the block cursor and re-scan a trailing overlap window each pass.

### 5. [MEDIUM] expireRevealed can strip an honest solver's bond and payout immediately after they win a challenge
- **Category:** dos
- **Location:** `contracts/src/P42SubmissionManager.sol:404`
- **Impact:** challengeEndsAt is set once at reveal (line 300) and never re-armed when a submission returns to Revealed after a dispute (resolveChallenge solver-prevails / expireChallenge). expireRevealed's expiry is the stale challengeEndsAt + challengeWindowSeconds. Because markChallenged allows a challenge in the exact final block (uses > not >=) and a dispute lasts exactly one window, a griefer files a bogus challenge at t0+W (posting a fully-refundable counter-bond), then at t0+2W atomically calls expireChallenge (->Revealed, bond refunded) then expireRevealed (->Rejected, honest solver's posting bond routed to treasury, recordCredit never called). The honest solver forfeits bond and rightful payout for near-free. Not a guaranteed kill — blocks t0+W and t0+2W are same-block priority-fee races a vigilant solver can contest — but the default outcome favors the attacker.
- **Fix:** On the solver-prevails branch of resolveChallenge, re-arm the finalize clock: submission.challengeEndsAt = uint64(block.timestamp) + challengeWindowSeconds (or track a separate finalizeGraceUntil = later of the original window and dispute resolution time), so an honest winner always gets a fresh full window to finalize.

### 6. [MEDIUM] atomsFromImprovement quantizes to a global 1e6 denominator, a million times coarser than the 1e-12 validity threshold
- **Category:** determinism
- **Location:** `agent/lib.mjs:9`
- **Impact:** atomsFromImprovement = floor(improvement * 1e6), while 8 verifiers accept improvements down to MIN_IMPROVEMENT = 1e-12. A verifier-valid improvement of 5e-7 floors to 0 atoms -> solver.mjs refuses to submit and reveal() reverts P42_ZERO_IMPROVEMENT: valid, verifier-accepted work is unsubmittable and unpayable. Worse, a client claiming 1 atom for that genuine improvement is auto-flagged FRAUDULENT by the operator (claimedAtoms > trueAtoms=0), risking an honest solver's bond, since the 1e6 convention lives only in the agent lib, not on-chain. Distinct improvements in the same 1e-6 bucket (1.4e-6 vs 1.9e-6 -> both 1 atom) are credited identically, misallocating proportional shares.
- **Fix:** Derive the atom denominator per problem from that problem's MIN_IMPROVEMENT (a pinned per-problem denominator >= 1/MIN_IMPROVEMENT) so no valid improvement rounds to zero and distinct valid improvements map to distinct atoms; carry the exact rational (or per-problem fixed denominator BUILD.md section 3 anticipates) on-chain instead of a global 1e6 scale.

### 7. [MEDIUM] Stale/expired runner lease permanently wedges the verifier queue — no reaper ships
- **Category:** dos
- **Location:** `src/p42_prizes/runner_queue.py:84`
- **Impact:** plan_runner_queue marks any running job with a missing/expired lease as 'stale_running' and short-circuits to decision='wait'/reason='stale_lease_reap_required' BEFORE any queued job can be selected. The only writer of lease_expires_at_utc is run_next_job_once (set, then cleared on normal finish); if the worker dies between those locked sections (reboot, OOM, kill — an untrusted forking payload can plausibly cause this), the job stays 'running' forever. No reap/requeue path exists (no CLI command, no other writer), and drain_runner_queue treats the wait as non-terminal and spins forever. The verifier oracle halts for all problems until a human hand-edits the queue JSON. VERIFIER_RUNNER.md says a supervisor must reap, but that tooling was never shipped.
- **Fix:** Reap inside the _locked_queue critical section: when a running job's lease is expired, atomically reset it to 'queued' (drop the lease, increment an attempt counter with a max-retries cap to avoid a poison-job loop), then proceed to selection. Add a runner-reap CLI command and/or fold the reset into plan/run_next_job_once so drain self-heals.

### 8. [MEDIUM] Operator's Revealed getLogs is unchunked and crash-loops on public-RPC range caps
- **Category:** dos
- **Location:** `agent/operator.mjs:73`
- **Impact:** scanOnce issues a single queryFilter(Revealed, fromBlock, latest) over the whole range with no chunking/retry, and fromBlock defaults to manifest.indexer.startBlock (deployment start, far behind head). Against the default public RPC (sepolia.base.org), a cold start scanning start->head in one eth_getLogs throws 'block range too large'/rate-limit; there is no try/catch in the for(;;) loop, so main().catch runs process.exit(1). Because fromBlock re-initializes from the manifest, every restart re-crashes on the same query — a deterministic crash loop disabling the only automated fraud-policing agent, and downtime spanning the 72h window lets fraudulent reveals finalize. The repo's own indexer already pages in 2000-block windows with retries for exactly this reason.
- **Fix:** Reuse the indexer's queryChunked pattern (paged windows + retry/backoff) for the operator's Revealed query, and wrap scanOnce in try/catch inside the polling loop so a transient RPC error logs and retries instead of terminating the daemon.

- **Impact:** The canonical manifest (deploymentCommit 3121a1a) records a P42SubmissionManager (0xafB0...) with a 7-arg constructor predating the DA refactor (995b568): no onchainDa/maxSolutionBytes, no sha256(bytes)==commitDaHash reveal gate (its reveal ABI lacks the bytes param), still treats permanenceHash as present. ### 12. [LOW] Problem freeze silently un-latches when a funded pool drains to zero, re-opening the anchored spec/verifier to owner mutation
- **Category:** immutability-invariant
- **Location:** `contracts/src/P42ProblemRegistry.sol:113`
- **Impact:** isFrozen() returns true only if the persisted frozen flag is set OR pool.funded() (== address(this).balance) > 0, and updateBeforeFunding gates only on isFrozen. Nothing on-chain auto-latches the monotone flag (fund() has no registry hook; the real deploy script never calls freeze()/latchFrozen), so if the permissionless latch is never called and the pool later drains to zero via claims, isFrozen regresses to false and a rogue/compromised owner can rewrite verifierImageHash and repoint modules — breaking the 'immutable on funding' docstring. Bounded: the registry is a pure metadata anchor settlement contracts never read, prevention is free (anyone calls latchFrozen once funded), and any rewrite emits a public event.
- **Fix:** Auto-latch at the source: have P42BountyPool.fund() call registry.latchFrozen(problemId) (or read a one-way everFunded bool) so freezing is atomic with funding and cannot regress; or drop the balance-derived fallback and require an explicit freeze() before any funding. Add latchFrozen to the funding runbook.

### 13. [LOW] Operator's bond-cap skip marks the largest frauds 'seen', declining to ever challenge them
- **Category:** economic
- **Location:** `agent/operator.mjs:160`
- **Impact:** When requiredChallengeBond(disputed) > --max-challenge-bond (default 0.01 ETH), the operator classifies the submission FRAUDULENT then does seen.add(key), so a running operator never revisits it in the 72h window. The counter-bond scales with the solver's own claimed atoms (betaBps=500 -> cap exceeded whenever disputed entitlement > 0.2 ETH), so on any meaningfully funded pool an attacker inflates past every default-capped operator; the biggest frauds are precisely the ones skipped. The persisted transcript is written before the bond check and records decision 'CHALLENGE' even when skipped, misstating the durable record. Bounded: challenge() is permissionless (a human/higher-cap operator can act), the cap is an intentional wallet-safety backstop, and seen is memory-only (restart re-scans).
- **Fix:** Do not seen.add on a bond-cap skip; surface a loud, persisted 'UNPOLICED FRAUD (bond over cap)' alert so a second operator/human can escalate, and make the cap a soft threshold requesting approval rather than a silent terminal skip. Fix the transcript to record the actual (skipped) outcome.

### 14. [LOW] Non-canonical verifier report is recorded valid=true and the job is marked 'succeeded'
- **Category:** correctness
- **Location:** `src/p42_prizes/runner_worker.py:421`
- **Impact:** result['valid'] = report.get('valid') is True is set at line 421 BEFORE the canonical-JSON check at 422; the early-return error branch leaves valid=True with ok=False. run_next_job_once then marks the queue job 'succeeded', and the loop event reports status='succeeded' while carrying reason='verifier report was not canonical JSON'. A verifier emitting valid=true in non-canonical bytes (unsorted keys, extra whitespace, NaN token) is refused yet recorded as accepted for any consumer keying off job status or transcript.verifier.valid. Bounded: the runner is outside the settlement trust root, no payout consumes queue status, and the mandated runner-alerts pass flags this ok=False/valid=True state as a critical quarantine alert; triggering requires the project's own verifier to emit valid=true non-canonically.

### 15. [LOW] Post-close rounding remainder and never-claimed entitlements are permanently stranded in the pool
- **Category:** economic
- **Location:** `contracts/src/P42PayoutLedger.sol:133`
- **Impact:** finalEntitlement floors each share, so Sigma(finalEntitlement) can be up to N-1 wei below distributablePool(). After close, fund() reverts, sweepFee only moves feeReserve, and consumeClaim caps each solver at their floored entitlement — no path recovers the remainder or any entitlement a solver never claims. Small bounded dust per close plus potentially unbounded never-claimed balances accumulate permanently, contradicting BUILD.md's documented 'round down, sweep to rollover' and the pro-rata CLOSE refund promise (neither implemented, and this gap is not tracked in GATE_LEDGER).
- **Fix:** Add a post-close, owner/treasury-only sweep of residual balance (balance - Sigma outstanding claimable) after a grace period, or assign the floor remainder deterministically to the largest-atom solver / treasury, so distributablePool is fully accounted for.

### 16. [LOW] Permissionless commit spam can stall ledger close() by keeping openSubmissionCount nonzero
- **Category:** dos
- **Location:** `contracts/src/P42SubmissionManager.sol:239`
- **Impact:** commit() is permissionless (only pausedNewActions + posting-bond floor gate it) and increments openSubmissionCount; close() reverts P42_OPEN_SUBMISSIONS while that count != 0, and a commit cannot be expired until committedAt + challengeWindowSeconds. An attacker who commits fresh junk faster than commits expire holds close() (and all pool payouts) hostage. Bounded: each spam bond is forfeited to treasury on expire (cost scales with pool via alpha), and the pause-then-close runbook (setPausedNewActions(true), wait one window, close) fully mitigates.
- **Fix:** Consider a per-sender open-submission cap or a bond floor high enough to make sustained spam uneconomical, and document the pause-then-close runbook.

### 17. [LOW] A single immutable guardian can veto every scheduled op, permanently halting all governance
- **Category:** guardian-abuse
- **Location:** `contracts/src/P42MultisigTimelock.sol:109`
- **Impact:** cancel() lets the immutable single-address guardian move any Pending op to Cancelled with no rate limit, bond, or override; a cancelled opId is terminal, and the guardian can cancel each fresh re-schedule (under a new salt) as it appears during the delay window. Signers are immutable with no rotation/override path and child contracts have immutable owners with no transferOwnership, so a compromised guardian yields permanent, unrecoverable denial of all privileged actions — not the 'worst case = delay' the docstring/GOVERNANCE.md claim. Not reachable on the live deployment (P42 is owned by a single EOA; the timelock was a standalone demo), and it yields DoS only, no theft.

## Appendix A — full confirmed finding detail (exploit scenarios)

Every confirmed finding with its concrete failure scenario, as produced by the finder and upheld by the adversarial verifier.

#### [CRITICAL] Self-/Sybil-challenge burns the single challenge slot and immunizes fraud at zero cost  ·  _contract-challenge-econ_
- **Where:** `contracts/src/P42ChallengeManager.sol:172` — economic
- **Flaw:** challenge() enforces exactly one challenge per submission (line 172: `if (existing.challenger != address(0)) revert P42_ALREADY_CHALLENGED()`) and never clears/allows a new challenge after resolution. It also does not require challenger != solver. Combined with expireChallenge() (lines 257-275), which returns the FULL posted bond to the challenger (line 267-268: `claimableBondWei[current.challenger] += refund`) and sets the submission back to Revealed, a fraudulent solver can consume the only challenge slot with a Sybil address at zero net cost. The submission's `resolved=true` slot then permanently blocks any honest challenge. This is exactly the flow the gate1 test at line 750 ('expires a stalled challenge...') exercises and blesses: it asserts the challenger's bond is fully refunded, status returns to Revealed (2), and the solver finalizes. Test gate1:579 confirms a second challenge always reverts ALREADY_CHALLENGED. The entire optimistic-verification security model (a bonded challenger can dispute inflated/invalid claims within the 72h window) is defeated.
- **Exploit / failure:** 1) Solver S reveals a fraudulent/inflated submission from address A; challengeEndsAt = now+72h. 2) In the same block (via a contract) S self-challenges from a controlled address B, posting the minimum required counter-bond and calling challenge(); markChallenged() sets status=Challenged. From this instant no honest party can call challenge() (reverts ALREADY_CHALLENGED) for the entire window and thereafter. 3) After 72h S calls expireChallenge(): B's bond is refunded in full (claimBond) and status returns to Revealed with resolved=true, so the slot can never be re-challenged. 4) S calls finalize() on the fraud, records credit, and claims the pool. Net cost to S: gas only. No honest challenger ever gets to dispute, and the trusted resolver has no on-chain challenge to act on.
- **Fix:** Do not gate challengeability on a single per-submission slot that a Sybil can occupy for free. Options, ideally combined: (a) allow multiple concurrent/sequential challenges (key challenges by an incrementing id or a mapping keyed by challenger) so a frivolous self-challenge cannot lock out others; (b) make a losing/expired challenge non-refundable (route an expired self-challenge bond to treasury, not back to the challenger) so slot-burning costs real value; (c) after a solver-favorable resolution or expiry, re-open the submission to fresh challenges for the remainder of (or a fresh) challenge window rather than marking it permanently immune. The design goal of not serially extending the window (gate1:579) can be met by capping cumulative added window time, not by making the first challenge a permanent one-shot lock.
- **Verifier verdict:** confirmed (sev→high) — The core mechanism is real and reachable in code. contracts/src/P42ChallengeManager.sol:163-198 (challenge) has no `challenger != solver` guard and enforces a single per-submission slot at line 172 (`if (existing.challenger != address(0)) revert P42_ALREADY_CHALLENGED()`). expireChallenge (lines 257-275) refunds the FULL counter-bond to the challenger (line 267-268) and, via P42SubmissionManager.resolveChallenge (line 373), returns the submission to Revealed so the solver can finalize (line 317-346). Tests gate1:579 (second challenge reverts ALREADY_CHALLENGED, window not extended) and gate1:751-792 (stalled challenge expires, full bond refunded, status back to Revealed=2, solver finalizes) bless exactly this flow. Concrete attack: solver reveals fraud from A, self-challenges from Sybil B in the reveal block (markChallenged sets status=Challenged), which makes every honest challenger's challenge() revert ALREADY_CHALLENGED for the whole 72h window; after the window the solver front-runs with expireChallenge (B refunded in full via claimBond) and finalizes. Net cost is gas plus a 72h capital lock of a refunded bond — effectively free. This is a genuine, permissionless DoS of the honest-challenger channel with no economic deterrent and no self-check.\n\nHowever, the finding overstates impact, so critical is not warranted. Its exploit step 3 claims "the trusted resolver has no on-chain challenge to act on" — that is incorrect: the Sybil challenge is a live Challenged submission that the resolver can adjudicate at any point in the window via resolve(submissionId, true, ...) (lines 200-249), rejecting the fraud regardless of who filed it or the (bogus) reasonHash. A diligent online resolver is not locked out. Full immunization requires an offline/passive/colluding resolver — but under that same condition expireChallenge already resolves ANY unadjudicated honest challenge in the solver's favor, so the fraud leaks even without the self-challenge. The bond is also value-proportional (requiredChallengeBond scales with disputedEntitlementWei, line 154-161), so for an inflated claim the attacker must lock real capital for 72h, not literally zero. Thus the incremental harm is removal of the permissionless bonded-alarm channel and a cheap lockout, not a standalone defeat of the model given the resolver backstop that Phase-1 explicitly relies on. Real and worth fixing (add challenger != solver, allow multiple/sequential challengers keyed by id, and/or forfeit an expired self-challenge bond), calibrated at high.

#### [HIGH] Operator advances fromBlock unconditionally, permanently dropping every 'leave for retry' submission (fraud goes unpoliced)  ·  _agent-clients_
- **Where:** `agent/operator.mjs:168` — dos
- **Flaw:** scanOnce() queries Revealed events in [fromBlock, latest] and, at the very end, sets `fromBlock = latest + 1` UNCONDITIONALLY. But many branches inside the loop deliberately `continue` WITHOUT adding the submission to `seen`, on the explicit promise that it will be retried later: reveal-tx not retrievable yet (line 101), calldata undecodable (line 100/104), off-chain reveal with no store configured (line 111/112), Arweave txid not found (line 116), Arweave fetch failed (line 119), local blob missing (line 122), and the sha256 anchor mismatch / tamper/unavailability path (line 135). The 'leaving for now / leave for retry' comments are therefore false: the retry never happens.
- **Exploit / failure:** A fraudulent off-chain-DA solver commits+reveals an invalid or inflated claim but does NOT post the solution bytes to the off-chain store yet. The operator's next scan hits `getBlob`/`findTxidByCid` -> DA MISS -> logs 'leaving for now' -> continue (not seen). At end of scan fromBlock jumps to latest+1. The solver now posts the real (or never posts) bytes; the operator's window has already advanced past the reveal block, so it never re-fetches, never re-verifies, and never challenges. After the 72h window the invalid/inflated submission finalizes and pays out. The same permanently-drops any submission that suffered a one-off RPC hiccup (tx not yet propagated) at the instant of the first scan.
- **Fix:** Do not advance fromBlock past unresolved events. Track the lowest block of any submission that was 'left for retry' this pass and set `fromBlock = min(latest+1, lowestPendingBlock)`, OR keep a persistent per-submissionId state machine (pending/verified/challenged) independent of the block cursor and re-scan a trailing overlap window each pass. At minimum, do not advance the cursor while any event in the window ended in a retryable continue.
- **Verifier verdict:** confirmed (sev→high) — Confirmed by direct code read. agent/operator.mjs:168 sets `fromBlock = latest + 1` unconditionally after the event loop, while seven branches (lines 100/101/104, 111-112, 116, 119, 122, 133-135) `continue` without `seen.add()` on an explicit "leave for retry" promise; the next scan's queryFilter (line 73) starts at latest+1, so those Revealed events are never re-queried — the retry structurally never happens for the process lifetime (daemon mode `for(;;)` at line 175). The contract provides no backstop: P42SubmissionManager.finalize() (contracts/src/P42SubmissionManager.sol:317-346) requires only Revealed status, elapsed window, and bond coverage — permanenceHash is unchecked and there is no DA-availability precondition — so an unchallenged off-chain-DA submission with withheld-then-late-posted bytes finalizes and records credit. Concrete path: solver on one of the 3 off-chain-DA problems reveals, withholds the blob through the operator's next 12s scan (DA MISS → continue → cursor jumps past reveal block), posts bytes late or never, finalizes an invalid/inflated claim after 72h. Also drops on-chain-DA submissions on a one-off RPC hiccup (lines 99-101). #### [INFO] Operator writes fetched solution to a predictable /tmp path (symlink-follow overwrite)  ·  _agent-clients_
- **Where:** `agent/operator.mjs:139` — key-handling
- **Flaw:** The operator writes the fetched blob to `${tmpdir()}/p42-op-${key}.json` where key is the submissionId — a fully predictable path in a world-writable directory. Node's writeFileSync follows an existing symlink at the target path.

## Appendix B — refuted findings (adversarial pass rejected these)

These were raised by a finder but did **not** survive independent verification — recorded for transparency and to show the settlement core fails closed where these attacks were attempted.

- **Solver-chosen improvementAtoms is unbounded; an unchallenged inflated claim overflows the ledger denominator and permanently bricks the pool for all other solvers** _(contract-core)_ — Premises are accurate: improvementAtoms is not bound by the commitment (commitPreimageWithDa binds only cid/solver/da/salt, confirmed) and reveal() only rejects ==0 (line 277). But the claimed overflow-brick exploit is unreachable. finalize() calls ledger.provisionalEntitlement(solver, improvementAtoms) at line 327 BEFORE recordCredit at line 337. In provisionalEntitlement (ledger line 111) the checked expression `distributable * (creditAtomsOf[solver] + additionalAtoms) / denominator` evaluates the multiplication first; with additionalAtoms ~= 2^256 and any nontrivial distributable (= poolBalance - reserve, reserve <= 2.5% since MAX_FEE_BPS=250), distributable*~2^256 overflows uint256 and reverts. So the attacker's OWN finalize reverts and the near-max credit is never recorded. Quantitatively: to record X the attacker needs distributable*X < 2^256 (X < 2^256/distributable); to brick honest finalizes X must be near 2^256 so X+h overflows at ledger lines 101/106. Both hold only when distributable ~= 1 wei (a worthless pool). For a real 1 ETH pool distributable~=1e18, max recordable X~=1.15e59, ~18 orders of magnitude below 2^256~=1.15e77 - honest solvers' recordCredit/provisionalEntitlement never overflow and finalize succeeds. Hence no permanent brick/denominator-overflow DoS as described. The residual is a dilution/overclaim (attacker with X~=1e59 captures ~100% of the pool), but that is the protocol's core optimistic-verification trust assumption, explicitly mitigated by the bonded-challenger + resolveChallenge bond-forfeiture path; the finding itself concedes Phase 1 may lack a challenger. Bounding improvementAtoms is reasonable defense-in-depth, but the overflow-brick exploit as written is refuted.
- **Registry minImprovementAtoms is not enforced anywhere in the on-chain submission lifecycle** _(contract-core)_ — The factual observation is accurate — P42SubmissionManager holds no registry reference and reveal() only checks improvementAtoms != 0 (contracts/src/P42SubmissionManager.sol:277), so P42ProblemRegistry.minImprovementAtoms is never enforced on-chain. But the concrete exploit is not reachable: (1) every real deployment registers minImprovementAtoms = "1" (deployments/base-sepolia/p42-prizes.json:120 and all other configs), making the != 0 check exactly equivalent to the registered minimum — the 'min=1000, reveal 1' state does not exist and registry metadata freezes once the pool is funded; (2) the gate is enforced where the optimistic design places enforcement: all 10 canonical verifiers hard-code `valid = improvement >= MIN_IMPROVEMENT` (e.g. problems/hadamard-668-defect/verifier/verify.py:113), so a sub-minimum claim is verifier-invalid on any public re-run and gets challenged/bond-slashed like any other invalid claim — 'finalizes if unchallenged' is the definitional optimistic assumption, not a distinct bug; (3) the claimed dilution harm is wrong: payout is improvement-proportional (src/p42_prizes/mechanism.py:86-115), so a 1-atom credit pays ~1 atom's pool fraction while costing bond + gas — honest solvers keep their exact Δ/ΣΔ share; (4) it is not silent/undocumented: contracts/test/RED_TEAM_COVERAGE.md row 10 states the on-chain floor is only the P42_ZERO_IMPROVEMENT gate with minImprovementAtoms 'anchored in the registry', and P42ProblemRegistry.sol:8 NatSpec calls the registry a 'metadata anchor'. Residual info-level note: verifiers gate improvement against SEED_BEST (not the moving frontier), so if a future problem registered min > 1 atom expecting enforcement, neither chain nor verifier would reject a sub-minimum frontier delta once the frontier moved past seed+MIN — worth a one-line doc clarification, not a live vulnerability.
- **Required challenge bond is inflatable by permissionless pool funding, enabling censorship of honest challenges** _(contract-challenge-econ)_ — Mechanism is factually correct: P42ChallengeManager.challenge() (line 177) sizes the counter-bond from submissionManager.disputedEntitlementWei() -> ledger.provisionalEntitlement() (P42PayoutLedger.sol:105-112), which reads the live pool.funded() (address(this).balance); pool funding via fund()/receive() is permissionless (P42BountyPool.sol:54-67); there is no snapshot and no cap on the betaBps*entitlement term. However, the exploit's impact claim (censorship of honest challenges) is refuted by the economics under the deployed parameters (betaBps=500 in every manifest): the challenge bond is only 5% of entitlement, so to force a challenger to lock an extra ΔB the attacker must inflate entitlement by 20·ΔB, which requires injecting ≥20·ΔB into the pool (more if the solver's share <1, since the remainder is donated to other solvers). Those injected funds are one-way — P42BountyPool has no withdrawal path (only claim() after close and payFee() exist), so the attacker's capital is locked until the pool closes (indefinite: gated on all open submissions resolving plus owner close()), while the challenger's bond is window-bounded, refundable on a win, and augmented by the forfeited solver posting bond. The attacker must also top up their own posting bond to alphaBps*E (2%) or finalize() reverts (P42SubmissionManager.sol:329). Net: a censor commits ≥20× the marginal bond they impose, for a strictly longer and less-recoverable term, and only one adequately-capitalized honest challenger (the bonded operator the optimistic model presumes) is needed to defeat the fraud. The literal reverting-tx event for an under-prepared challenger is real but is a re-quote (send the public required at tx time), not censorship. Residual low-severity hardening value in snapshotting the bond basis at reveal, but the medium censorship exploit does not hold.
- **Commit-time posting bond is α × the ENTIRE pool, not α × entitlement — over-collateralizes marginal solvers and gives funders a griefing/exclusion lever** _(mechanism-econ)_ — The mechanics are accurately described (commit bond = alphaBps × pool.funded() at P42SubmissionManager.sol:218-220 vs alpha × entitlement at finalize, lines 327-331), but the finding fails as an exploit or spec divergence on four grounds. (1) It is the repo's explicit documented design: docs/LAUNCH_GATES.md:28 gates on 'Posting bond scales to alpha * pool_at_submission' and docs/GATE_LEDGER.md:54 records test coverage for it; and since entitlement ≤ pool (P42PayoutLedger.sol:105-112), alpha·pool literally satisfies the stated 'bond >= alpha * entitlement' invariant. (2) The 'over-collateralization' premise misreads the payout math: under Δ_i/ΣΔ_j pro-rata with blind commits, a solver with any small Δ can end up entitled to 100% of the pool if no other credit is recorded, so alpha·pool is the tight upper bound on possible entitlement at commit time — the proposed solver-declared ceiling is unsound because a solver cannot bound their share of a denominator determined by future submissions. (3) The griefing lever is economically self-defeating: fund() deposits are irrevocable and paid out to solvers, so raising the toll by alpha·ΔP (alpha = 1-20% in all configs) costs the griefer ΔP permanently — 5x-100x the temporary lockup increase it imposes — while proportionally raising the solvers' reward. (4) The commit bond is fully refunded to honest solvers at finalize (_makeBondClaimable line 335, claimBond line 414), so it is a ~days-long capital lockup, not a cost, and topUpBond already handles the pool-grows-after-commit case. The residual kernel — capital-constrained small-Δ solvers need liquidity scaling with pool size — is an inherent, documented trade-off of blind-commit pro-rata design, worth at most an informational note, not a vulnerability.
- **Solver-controlled solutionCid is interpolated unsanitized into the Arweave GraphQL query (injection)** _(agent-clients)_ — The code facts are accurate: agent/da-arweave.mjs:47 interpolates the solver-controlled `cid` into the GraphQL query string with no sanitization, operator.mjs:115 feeds it ev.args.solutionCid unmodified, and P42SubmissionManager.sol:276 only rejects an empty solutionCid (no sha256/hex format constraint), so GraphQL-layer injection is genuinely reachable on the --arweave path. However the claimed exploit impact is refuted. (1) The injection grants no capability beyond a trivial well-formed alternative: making findTxidByCid return null is equally achievable with a syntactically valid CID that simply points to nothing on Arweave; the operator hits the identical `DA MISS ... leaving for now` branch (operator.mjs:116) either way. This is a data-availability/withholding concern, not an injection one. (2) The only outcome that would let fraud pass verification — substituting different bytes — is blocked by the integrity gate at operator.mjs:131-136 (sha256(blob)===commitDaHash); any crafted txid's bytes that don't hash to the anchor are refused, and any that do are by definition the real committed solution (collision resistance), yielding an honest re-verify. The finding concedes this. (3) No crash/DoS: the response is parsed with optional chaining inside try/catch, so a malformed query just returns null after retries. (4) Reachability is narrow: ARWEAVE defaults false (line 44); the 7 on-chain-DA problems read from calldata and never call findTxidByCid. Net: a real code-hygiene defect (should validate ^sha256:[0-9a-f]{64}$ and use a $cid GraphQL variable, ideally cross-check cid===sha256:+commitDaHash), but not a medium-severity security exploit since it adds no adversarial power and the fraud-enabling path is independently mitigated.
- **runVerifier JSON.parse of trimmed multi-line stdout throws and can kill the operator daemon** _(agent-clients)_ — The code reading is accurate (agent/lib.mjs:27-29 parses the whole trimmed stdout; agent/operator.mjs:141 calls runVerifier with no try/catch, so a throw hits main().catch and process.exit(1) at line 177), but the trigger condition is not reachable: every one of the 10 verifiers in problems/*/verifier/verify.py is deliberately "total" — the single stdout write is one print(report.to_canonical_json()) call, and all attacker-influenced paths are wrapped in except VerifierFailure plus a catch-all except Exception (e.g. hadamard-mini/verify.py:101-114) that converts any error into the canonical report. canonical_json (src/p42_prizes/verdict.py:23-26) uses json.dumps with ensure_ascii=True, so newlines embedded in attacker-controlled detail strings are escaped — the report is provably a single line. Python warnings/deprecation notices and tracebacks go to stderr (never captured into `out`), there are no debug prints, tqdm, or logging-to-stdout anywhere in the verifiers, argparse cannot error (the operator passes the fixed --solution flag), and the solution file always exists because the operator writes it itself at operator.mjs:140. Therefore no crafted solution can produce multi-line stdout and no concrete crash scenario exists in the current code. What survives is a defense-in-depth note, not a bug: the operator's crash-on-throw pattern plus whole-blob JSON.parse is fragile against future verifier edits (any added stdout line would crash the daemon and, since seen.add happens only after verification, re-crash on every restart). Hardening as suggested (parse last non-empty line, per-submission try/catch) is cheap and sensible, but as a finding it is hypothetical — severity info, verdict refuted.
- **On-chain problem registration anchors verifierImageHash/admissionMatrixHash with no committed preimages — unverifiable evidence anchors** _(honesty-supplychain)_ — The finding's load-bearing claim — "No artifact in the repo hashes to either value" — is factually false. Keccak256-hashing every file at the manifest's recorded deploymentCommit (3121a1a) shows all four on-chain anchors have committed preimages: verifierImageHash 0x716c0bae... = keccak256(problems/hadamard-mini/Dockerfile), admissionMatrixHash 0xb2e3455a... = keccak256(problems/hadamard-mini/solution.schema.json), specHash = keccak256(SPEC.md), verifierSourceHash = keccak256(verifier/verify.py). All four files are unchanged at HEAD, so the anchors are byte-for-byte reproducible from the current repo — the auditor only tried sha256 and string hashes. The 'unverifiable opaque anchor' exploit therefore does not exist. Residual issues are much weaker and already mitigated: (1) the manifest lacks a provenance note saying which file each hash covers (a reviewer must brute-force it, as I did) — a documentation nit; (2) verifierImageHash pins the Dockerfile rather than a built image digest and admissionMatrixHash pins the solution schema rather than a real four-host matrix — but docs/GATE_LEDGER.md (lines 67-68, 81) openly states the pinned image digest and collected matrix do not exist yet and blocks funding on them, and admit-ready rejects placeholder images/matrix mismatches, so nothing is 'silently violated'. hadamard-mini is an explicitly labeled phase-0 testnet fixture with no funded pool.
