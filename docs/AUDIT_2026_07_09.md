# P42 Prizes - Fresh Full-Protocol Audit

**Audit date:** 2026-07-09

**Audited snapshot:** `454f44d9c8299568217d34c60d21d784ff4507e4`

**Branch:** `claude/prize-protocol-signal-design-7bea8m`

**Scope:** mechanism, all Solidity contracts, challenge/resolver flow, solver/operator/indexer, Python runner and admission tooling, all ten verifier packages, portal/API, deployment evidence, governance, legal/compliance gates, and public launch claims.

## Verdict

**NO-GO for real ETH and NO-GO for a canonical Base Sepolia settlement pilot on this snapshot.**

The repository is a useful Phase-0 math-competition prototype with a strong exact-arithmetic direction, but it is not a production settlement system. Five independently confirmed mechanism paths can award or capture value contrary to the stated design, the live verification path bypasses the hardened queued runner, and the current deployment/evidence set does not prove the audited source.

This verdict does not mean the project should stop. It means the next milestone is a correctness remediation release followed by a fresh canonical testnet campaign, not mainnet or real-value funding.

No real ETH is at risk while the existing stop conditions remain enforced.

## Method

- Froze the review at commit `454f44d`; local HEAD and upstream matched at audit start.
- Ran independent read-only passes over mechanism/contracts, verifier/math packaging, web/API, production/deployment, and full specification conformance.

- Probed the live Render portal, current Base Sepolia evidence, indexer, and reconciliation command.
- Executed audit-only local Hardhat reproductions for the highest-risk state-machine findings. No transactions were sent to a public chain.
- Distinguished source correctness from deployment readiness and from external legal/audit attestations.

## Executive Summary

The strongest part is the local mathematical scorer work: current verifier tests pass, exact rational/integer scoring is used, claimed scores are generally recomputed, and no new false-acceptance bug was found in the current ten Python scorers. The prior C3 signed-maximum bug is fixed in source.

The weakest part is the boundary between a correct scorer and money. The contracts do not enforce several economic phase and ordering assumptions that the design treats as closed. In particular:

1. a pre-arm commit can become paid when `commit` and `armFunding` share a block timestamp;
2. a searcher can commit and reveal a copied pending solution in the same block, then win the finalize-order race;
3. a solver can finalize against an empty pool, recover its floor bond, and later receive an arbitrarily larger donation-funded entitlement;
4. a resolver decision changes submission state immediately, while the advertised fraud window can only slash a fixed bond and cannot reverse the decision; and
5. an off-chain-DA submission can finalize even when nobody can retrieve its bytes, while the current operator explicitly retries instead of challenging that condition.

The operational trust boundary is also incomplete. The live JS operator watches chain reveals but executes verifier Python directly on the host with inherited environment and no timeout. The safer Python queue has OOM planning, leases, sandbox support, and better transcripts, but it is not wired to chain events or claimed-score/challenge transactions. The two paths do not form one production verifier service.

Finally, the evidence plane has drifted. The canonical Base Sepolia deployment predates the current DA/frontier/funding source; current reconciliation fails on the public RPC range cap; the indexer can omit lifecycle events and still print `OK`; verifier admission can accept a self-declared matrix without executing the named image; a recorded C3 image reflects the known-unsound pre-fix scorer; and nine of ten root seed-verification targets now fail after the latest seed refresh.

## Confirmed Findings

### C1. OPEN-phase commits can become paid in the arm block

`commit()` stores only `block.timestamp`, while `finalize()` treats `committedAt >= armedAt` as paid ([P42SubmissionManager.sol](../contracts/src/P42SubmissionManager.sol), lines 374-390 and 531-565). All transactions in one block share a timestamp.

Local reproduction:

```text
commit transaction index: 0
armFunding transaction index: 1
same block: true
committedAt == armedAt: true
ledger credit recorded: 100e18 atoms
```

This violates the stated invariant that work committed in the free phase earns zero forever. Store `paidAtCommit = fundingArmed` or an immutable phase id in each submission. A timestamp cannot encode transaction order within a block.

### C2. Commit-reveal does not stop pending-reveal sniping

There is no minimum commit age between [commit](../contracts/src/P42SubmissionManager.sol) and [reveal](../contracts/src/P42SubmissionManager.sol) (lines 364-393 and 425-492), despite the `T_commit` flow described in [BUILD.md](BUILD.md). A searcher that sees a pending reveal can create its own address-bound commitment and reveal it in the same block before the original reveal.

Local reproduction placed the searcher's commit, searcher reveal, and original reveal in one block. The searcher revealed first, finalized first, received `100e18` credit and the entire 10 ETH provisional entitlement; the original solver received zero credit.

The CID being inside the commitment prevents rebinding somebody else's old commitment. It does not prevent a fresh commitment made after the solution becomes public unless the contract enforces commitment maturity.

### C3. Late donations reopen the bond-leverage failure

Finalization makes the posting bond claimable immediately ([P42SubmissionManager.sol](../contracts/src/P42SubmissionManager.sol), lines 540-566). Funding stays open until ledger close ([P42BountyPool.sol](../contracts/src/P42BountyPool.sol), lines 138-154), and entitlement uses the later close balance ([P42PayoutLedger.sol](../contracts/src/P42PayoutLedger.sol), lines 156-184).

Local reproduction:

```text
pool at submission/finalization: 0 ETH
posting bond: 0.01 ETH
bond recovered: yes
donation after finalization: 100 ETH
final entitlement: 100 ETH
```

This is the original leverage problem shifted in time. `alpha * pool_at_submission` cannot collateralize money added after the bond is returned.

### C4. The resolver fraud window cannot correct a resolver lie

`resolve()` immediately routes challenge bonds and calls `resolveChallenge()` ([P42ChallengeManager.sol](../contracts/src/P42ChallengeManager.sol), lines 209-257). `slashResolverBond()` only moves the resolver bond to treasury (lines 309-320). It does not restore submission status, reopen the challenge slot, return the victim's bond, or reverse credit/frontier state.

A solver-favorable decision leaves the old challenge record occupied while returning the submission to `Revealed`, so a second challenger receives `P42_ALREADY_CHALLENGED`. Local reproduction then slashed the resolver bond and still finalized the approved claim for `100e18` credit.

The current fraud window is a bond holding period, not decision finality. This directly contradicts the design statement that no resolver decision is final until the fraud-proof window closes.

### C5. Off-chain payload absence is not fail-closed

For `onchainDa == false`, the contract requires empty reveal bytes and stores only an anchor plus arbitrary nonempty CID ([P42SubmissionManager.sol](../contracts/src/P42SubmissionManager.sol), lines 425-479). The operator treats an unavailable or hash-mismatched payload as retryable and does not challenge it ([operator.mjs](../agent/operator.mjs), lines 128-156).

The challenge clock continues while the payload is absent. Therefore an invalid claim can reveal an unavailable anchor, remain unverifiable, and finalize unless an independent actor implements a missing-DA challenge policy. The current automated path does not.

An anchor proves integrity of bytes if they are found. It does not prove that bytes are available.

### H1. The hardened runner is not the live runner

The live [operator](../agent/operator.mjs) watches `Revealed` events and calls [runVerifier](../agent/lib.mjs), which executes host `python3` with `execFileSync`, no timeout, and the full inherited environment (operator lines 87-164; lib lines 89-101).

The Python [runner worker](../src/p42_prizes/runner_worker.py) has queue leases, OOM planning, process isolation, optional Docker execution, and canonical transcripts, but accepts local jobs rather than chain events and does not bind a queued report to an on-chain claimed score or challenge transaction. Its CLI also does not expose the Docker sandbox policy, whose default remains `none`.

Production needs one path, not a safe demonstration lane and a separate live lane.

### H2. A refunded challenge can be recycled forever

`expireChallenge()` fully refunds the challenger, deletes the challenge, and returns the submission to `Revealed` ([P42ChallengeManager.sol](../contracts/src/P42ChallengeManager.sol), lines 260-292). `resolveChallenge(false)` rearms a fresh full window ([P42SubmissionManager.sol](../contracts/src/P42SubmissionManager.sol), lines 658-665).

Local reproduction used the same challenger for two fully refunded expiry cycles and successfully opened a third. `openSubmissionCount` stayed at one throughout, so `ledger.close()` remained blocked.

The F3 repair correctly avoided permanent one-shot immunity, but without a maximum horizon it introduced unbounded serial delay.

### H3. Replay and reconciliation can report confidence they have not earned

The canonical manifest records the older `3121a1a` deployment, which predates the current 11-argument submission manager and its DA/open-witness/frontier behavior ([p42-prizes.json](../deployments/base-sepolia/p42-prizes.json)). The committed reconciliation report proves that old deployment, not this audit snapshot.

Fresh checks found:

- current reconciliation failed because the public Base RPC limits `eth_getLogs` to 2,000 blocks while [reconcile-base-sepolia.js](../contracts/scripts/reconcile-base-sepolia.js) queries the full range;
- the fresh [indexer](../agent/indexer.mjs) printed `reconstruction vs chain: OK (6/6)` with zero reveals even though the committed historical report records a reveal;
- indexer reconciliation compares pool/ledger totals but not `submissionCount` or complete lifecycle state; and
- `CreditVoided` and `FinalizeVoided` are not replayed, so governance recovery cannot be reconstructed deterministically.

No gate should accept `OK` unless the deployed runtime code/ABI, event range, lifecycle counts, and recovery events all match.

### H4. Verifier admission is not bound to the verifier image

[admit-host](../src/p42_prizes/admission.py) executes the local checkout, not the image named in `problem.yaml`; host identity is CLI-overridable; and [admit-ready](../src/p42_prizes/readiness.py) checks digest syntax and matrix equality rather than pulling and executing the digest. Tests intentionally demonstrate admission with a fabricated `sha256:aaaa...` image and self-declared hosts.

The repository also carries stale high-risk evidence: [verifier-images.json](../deployments/base-sepolia/verifier-images.json) records the signed-autoconvolution C3 example as valid under a pre-fix image, while current `verify.py` v0.1.1 correctly rejects it. The problem manifest and portal still advertise verifier v0.1.0.

An exact verifier is only a trust root if the admitted bytes, deployed image, runner image, source commit, and public report are cryptographically the same object.

### H5. Close and governance liveness are not production-complete

Ledger close is permanently owner-only and has no immutable close-by timestamp ([P42PayoutLedger.sol](../contracts/src/P42PayoutLedger.sol), lines 156-167). A lost or censoring owner can lock every payout. Conversely, the owner can close as soon as open submissions reach zero; the decided idle/earliest-close policy is not enforced.

The submission manager does not reject commits after ledger close. A local reproduction closed the ledger, accepted a new commit/reveal, reverted positive-credit finalize with `P42_CLOSED`, then allowed expiry to transfer the solver's 0.01 ETH bond to treasury.

The pool's `funded()` view returns its raw ETH balance ([P42BountyPool.sol](../contracts/src/P42BountyPool.sol), lines 97-99), and the registry derives/latches frozen metadata from that value ([P42ProblemRegistry.sol](../contracts/src/P42ProblemRegistry.sol), around line 102). ETH forced into the contract can therefore bypass `fund()` and `fundingArmed`, strand value, and make an otherwise unfunded draft appear funded. The policy's explicit monotone `everFunded` and freeze-before-fund state is not implemented.

The production deploy script also rejects `owner != deployer` and does not deploy the documented multisig/timelock topology. The existing Base Sepolia owner, treasury, resolver, and deployer are one EOA.

### H6. The autonomous agent flow is not durable under concurrency or AA wallets

[solver.mjs](../agent/solver.mjs) submits a commit and then reads global `submissionCount()` to infer its id (lines 203-209). A concurrent commit can make it reveal another solver's id while its own bond remains locked. The id must come from the caller's `Committed` receipt.

The solver waits the original challenge deadline and then attempts one finalize. It does not persist/recover through `Challenged`, resolver outcomes, rearmed windows, bond top-ups, retries, or process restarts.

The operator decodes the top-level transaction as `SubmissionManager.reveal`. A reveal forwarded through `P42AgentWallet.execute` or an ERC-4337 bundler is an internal call, so the top-level calldata is not `reveal` and the operator leaves it unverified. The included wallet additionally limits target/selector/value but not problem id, expected commitment, calldata fields, chain id, or expiry.

### H7. The live portal is a demo, but some controls imply more

An unauthenticated invalid mutation POST to both the public `/prizes` proxy and direct Render origin reached body validation instead of returning the configured pre-parse `401`. The production source has an opt-in API-key gate, but the live environment is not enforcing it ([api-auth.ts](../web/src/lib/api-auth.ts), lines 34-52).

The portal's local frontier counts `revealed` and `challenged` submissions as credited before challenge finality ([frontier.ts](../web/src/lib/frontier.ts), lines 11-38), unlike the chain. Its local commit format is `p42:v0`, while the current contract uses the DA-bound `p42:v1` format.

All ten displayed donation addresses are synthetic `0x4242...0001` through `...0010`. Fresh Base Sepolia checks found no bytecode, nonce, or balance at any of them. The UI labels the action `Deposit`, while chain provenance admits `poolAddress: null`. Even test ETH should not be sent to inert addresses.

### H8. The release ledger is not currently reproducible

The full unit suites pass, but the release command does not:

- `make verify-seed` now passes only Hadamard Mini and fails the other nine boards with `NOT_STRICT_IMPROVEMENT`;
- `make admit-host-erdos` fails with `unsupported exit code 2` because Make converts the verifier's valid-report/invalid-eligibility exit 1 into exit 2;
- the gate ledger still marks `make verify-seed` as passing;
- all ten problem manifests still use `sha256:local-dev`;
- no current ten-board attested N-host/two-glibc matrix exists;
- `.github/workflows/ci.yml` is not published and the deployment branch is not protected; and
- `agent/npm audit --audit-level=moderate` reports 29 advisories, including one high advisory through the deprecated, unconditionally imported `@irys/sdk` stack.

### H9. External production gates are correctly open

No external smart-contract audit, counsel-signed legal memo, governance signoff, incident drill, live bug bounty, Terms, Privacy, Risk Disclosures, or Tax Reporting policy is committed. Validators prove only that a JSON packet has the expected shape; they do not authenticate counsel, signatures, chain configuration, or external evidence.

The Coinbase Onramp route is correctly disabled today. Before enablement it must use the current server-side JWT/session-token flow, bind the required trusted client IP, and be limited to reviewed mainnet pool addresses. Legal classification, sanctions screening, tax reporting, custody, and international access remain questions for licensed counsel, not software validators.

Relevant primary guidance: [Coinbase Onramp session tokens](https://docs.cdp.coinbase.com/api-reference/rest-api/onramp-offramp/create-session-token), [FinCEN convertible virtual currency guidance](https://www.fincen.gov/resources/statutes-regulations/guidance/application-fincens-regulations-certain-business-models), [OFAC virtual-currency guidance](https://ofac.treasury.gov/system/files/126/virtual_currency_guidance_brochure.pdf), and [IRS taxable income guidance](https://www.irs.gov/filing/taxable-income).

## Secondary Correctness Findings

- The contract implements a fixed atom `minImprovement` floor and zero-credit supersession, while `BUILD.md` specifies a fraction of the current remaining gap, rejection/slashing, and `RESOLVED` retirement.
- `BUILD.md`, the Python mechanism simulator, and Solidity disagree about funder refunds, zero-credit pools, and fee timing. Python also rounds per credit row while Solidity aggregates per solver.
- The verifier lint can be bypassed with imported aliases such as `from builtins import float as f`; canonical JSON currently permits Python `NaN`, which JavaScript rejects.
- All ten verifiers read the full untrusted file before checking the size limit, and missing files can emit tracebacks instead of a total `VerdictReport`.
- Several JSON schemas are looser than the actual verifier parser, so schema-valid agent output can still lose a bond.
- The portal JSON store rewrites and fsyncs the whole state per mutation, returns the complete event history, and has non-transactional idempotency. It is not suitable for multi-instance or adversarial load.
- Public copy still mentions ETH/USDC and a 5% fee cap in places, while current contracts are ETH-only with an immutable 2.5% maximum and the old deployment uses 0%.

## Blue-Team Results

The audit also tried to falsify several prior concerns. These properties held in source/tests:

- Payout credit is now marginal against the live on-chain frontier, so simple identity splitting telescopes and does not create denominator value.
- Solver claims are unavailable before close, and close snapshots the denominator/pool, closing the original vesting-versus-dilution overpayment.
- `claim()` is deliberately unpausable and uses pull payment with a reentrancy guard.
- Accepted score atoms are range-bounded before marginal subtraction, preventing the earlier signed-overflow panic path.
- On-chain-DA reveals enforce nonempty bounded bytes and `sha256(solution) == commitDaHash`.
- Current verifier source recomputes ordinary claimed scores, uses exact arithmetic, and the C3 L-infinity scorer is fixed.
- The Docker build context is deny-by-default; the earlier context/key leakage concern is closed.
- Web and contract dependency audits are currently clean.

These are real improvements. They do not compensate for the five critical boundary failures above.

## Remediation Order

1. **Stop misleading value surfaces.** Enforce live mutation auth, remove inert deposit actions, and keep Onramp disabled.
2. **Repair the economic state machine.** Fix same-block phase identity, commit maturity, late-funding collateral, resolver reversibility/finality, off-chain DA failure semantics, maximum dispute horizon, and post-close commits. Add one regression per reproduction above.
3. **Unify autonomous verification.** Chain event -> persistent queue -> enforced container/OOM policy -> exact claimed-score comparison -> canonical public transcript -> bounded challenge transaction -> resolver/finality tracking.
4. **Close the verifier supply chain.** Rebuild/revoke stale images; bind commit, source tree, image digest, host attestation, and report; fix seed/admission commands; run all ten boards on the real matrix.
5. **Create one canonical testnet truth.** Governance-owned deployment from a protected release SHA; ABI/runtime/config hashes; chunked indexer/reconcile; recovery-event replay; current adversarial campaign.
6. **Obtain independent gates.** External contract audit and retest, independent mathematical review of each funded problem reduction, counsel memo and public policies, governance/incident rehearsal, then a capped testnet-to-mainnet decision.

## Confidence And Residual Gaps

Confidence is high that the listed critical/high findings are real because each is tied to current source and the top contract failures were reproduced against locally deployed bytecode. Confidence is not and cannot be 100%: no formal verification, exhaustive state-machine fuzzing, independent smart-contract audit, independent mathematical proof review, or complete live-chain lifecycle was available.

The correct production standard remains the one already written in the gate ledger: no known unresolved critical/high risk, reproducible evidence for the exact deployed artifacts, and external attestations where software cannot self-certify.
