# Source-release evidence v3 foundation

Status: implemented as a fail-closed foundation; not activated and not a current production receipt.

## Security boundary

V3 separates three authorities that v2 allowed the target repository to describe for itself:

1. `/etc/p42/source-release-trust-root.json` is a root-owned, non-group/world-writable local root read with `O_NOFOLLOW` and stable file-identity checks. It pins the equally protected policy path and digest plus the only allowed bootstrap artifacts. Production current validation accepts no caller policy, digest, report path, or offline override. Before any Git-derived trust operation, validation rejects replacement refs (loose or packed), grafts, object alternates, and inherited repository/object/config override variables. Default Git subprocesses also use `--no-replace-objects`, `GIT_NO_REPLACE_OBJECTS=1`, and disabled global/system config. A separate root-owned `/etc/p42/source-release-executables.json` manifest binds absolute paths and SHA-256 identities for exactly `git`, `gh`, `render`, `node`, and `curl`, a protected validator-owned runtime directory, and the complete Git smart-HTTP helper closure. On the supported Linux auditor host, every direct tool must be a native binary. Every invocation traverses the executable, `HOME`, runtime, and Git-helper hierarchies root-to-leaf with descriptor-relative `O_NOFOLLOW` opens, rejects symlinked or group/world-writable components and non-root ownership, retains verified descriptors through process creation, and executes the exact hashed tool inode through `/proc/self/fd`. Git receives a held sealed-empty `GIT_GRAFT_FILE` descriptor and a held `GIT_EXEC_PATH` directory whose exact canonical tree digest permits only `git-remote-https` plus `git-fetch-pack`, `git-index-pack`, and `git-unpack-objects`; the three builtin dashed entries must be hardlinks to the pinned Git inode and Git must advertise all three as builtins. Ambient helper, askpass, SSH, config, `PATH`, and `TMPDIR` resolution is rejected or omitted. The validator fails closed when exact-inode execution is unavailable.
2. The threshold-signed policy pins the repository, branch, activation commit, canonical Render service, exact workflow bytes, closure algorithm `p42-git-ls-tree-closure/v1`, stable closure roots (`["."]`), exact ordered seven-job set (the four ordinary producers, both SP1 image producers, and the cross-image `SP1 objective-program reproducibility` comparator), genesis receipt, deploy/evidence path policies, independent reviewers, and direct 32-probe semantics. The probes cover the original 12 portal/API observations plus both origins of every exact-ten funding-target route, whose launch state must be the exact fail-closed v3 envelope with `target: null`. Authority IDs and decoded Ed25519 public keys must both be unique.
3. The receipt chain is recursively loaded from committed Git bytes until it reaches the policy-pinned genesis. For backward compatibility without creating an unauthenticated v3 checkpoint, that signed genesis reference must resolve to the intended legacy v2 receipt; a v3 receipt is never accepted as genesis. Each link must be the latest canonical receipt before the next receipt's publication commit; every receipt hash, schema, canonical path, publication commit, observed head, and publication transition must lie on first-parent `main` history. Every predecessor v3 interval is then replayed oldest-to-newest: its source provenance, inherited or advanced deploy pointer, and protected bootstrap authority must validate before its self-asserted observed head can become the next baseline.
4. Every first-parent commit in the predecessor-to-observed interval requires authorization, regardless of whether it changes contracts, verifier source, workflows, problems, schemas, deployment source, or another tracked path. The sole ordinary exemption is a commit with a nonempty changed-path set entirely contained in the threshold-signed policy's `evidenceOnlyPaths`. Empty commits and mixed evidence/source commits still require authorization. An evidence-only receipt publication can advance the chain only after its claimed predecessor interval replays successfully; committed receipt bytes never self-authorize a new baseline.
5. Online validation first captures authenticated GitHub `main`, then fetches that exact object ID from the fixed canonical HTTPS remote into a mode-0700 repository and worktree beneath the protected validator runtime directory. It runs strict full object verification before checkout and again after the private mutation boundary, removes `FETCH_HEAD`, and rewrites every later `HEAD` expression to the captured object ID while rejecting mutable branch, remote, and fetch references. All commit, parent, tree, blob, workflow, receipt, and guard reads use that content-addressed snapshot; caller checkout metadata is never consulted after the initial fail-closed environment/replace/graft/alternate preflight. Every Git invocation independently binds graft resolution to the held sealed-empty descriptor, so even a same-UID graft inserted into the private snapshot between fetch and lineage replay cannot enter authority history. It compares the fetched object to the authenticated head before applying the activation/downgrade rule, then authenticates the exact GitHub run attempt/jobs, merged PR and PR-head tree for every current and historical provenance row, allowlisted non-author approvals at each exact head and submitted unambiguously before the authenticated merge time, canonical Render deployment, and evidence-only publication tail. Equal timestamps fail closed because GitHub timestamps do not establish ordering within the second. It pins and executes the committed 32-probe guard plus its board manifest, compares the guard's exported routes to the signed policy, and independently binds marker/API/final-URL/equivalence observations.

The commands are deliberately distinct. `source-release-evidence-validate` preserves historical v2 archive validation, including binding the recorded board projection to the manifest committed at the receipt's authenticated `observedBranchHead` rather than a later checkout head. `source-release-current-validate` always loads the canonical committed receipt and protected local root, authenticates remote `main`, and fails closed on every operational error. Its public Python and CLI surfaces accept no command runner, Git-blob loader, network reader, clock, policy, receipt provider, or remote override; production execution is sealed to the audited implementations and fixed canonical remote, while dependency injection and alternate remotes exist only in private test helpers. The boundary assumes the installed Python auditor process and root account are trusted; arbitrary same-process code or root compromise is outside scope. Once authenticated remote `main` descends from `activationCommit`, v2 is rejected.

## Direct pushes and bootstrap

Every authorization-required first-parent source commit must have exactly matching merged-PR coverage. A direct push to `contracts/`, `src/`, `.github/`, `problems/`, `schemas/`, deployment source, or any other non-exempt path fails current validation even when a later evidence PR tries to mask it. A PR approval submitted after the merge does not authorize that merge.

The only exception is an explicit `p42-source-release-bootstrap-ratification/v1` artifact. It binds the full policy digest, authorization ID, expiry, and a closed contiguous interval: covered commits, first parent, final tree, and aggregate changed-path digest. The protected root must allowlist its exact digest/path/expiry, and it must meet the policy threshold with valid Ed25519 signatures. Recursive replay applies the same checks to historical intervals and fails closed when a historical ratification is missing, altered, or expired. There is no unsigned, caller-supplied, or repository-local bypass.

Bootstrap ratification is for a disclosed migration interval only. It does not make an unreviewed direct push retrospectively PR-reviewed.

## Receipt fields added in v3

- `previousEvidence`: publication commit, repository-relative path, observed head, deploy commit, and canonical receipt hash.
- `trustPolicy`: external policy ID and hash.
- `ci`: workflow ID, path, raw-blob SHA-256, Git blob OID, closure algorithm/roots, immutable external refs, and run attempt in addition to the v2 run identity. Each receipt enumerates every Git entry under the policy roots at its own observed head and binds the ordered manifest with SHA-256. The policy does not pin that per-release digest, so a later source tree can produce new complete evidence without changing the closure rules.
- `deployProvenance`: predecessor baseline and an ordered, complete list of every authorization-required first-parent source commit with first parent, tree, changed-path digest, and PR or bootstrap authorization. Current validation recursively re-derives and authenticates this field for every predecessor v3 receipt before trusting its baseline. The historical field name is retained for v3 compatibility; its scope is not limited to Render-deploying paths.
- `deployRelevantCommit`: independently derived as the latest first-parent commit touching the policy-pinned Render paths (`web/` or `render.yaml`), or inherited from the predecessor when none do. `render.serviceId` is fixed to `srv-d96pokeq1p3s73foqk60`, and Render runtime/live commits must equal this separate pointer.
- `releaseGuard`: exactly 32 observations: the original 12 v3 portal/API observations plus paired direct/public funding-target probes for every exact-ten board. The historical v2 10-probe archive contract is unchanged. The asserted command is the policy-pinned committed `node scripts/verify-render-release.mjs`, not an unbound command label.

## Activation ceremony

Activation is intentionally incomplete. The owner/release authorities must:

1. Provision independent Ed25519 custody for at least three release authorities and approve a threshold of at least two.
2. Review and sign one immutable external `p42-source-release-policy/v1` artifact. It must contain the final activation commit, genesis receipt, exact workflow identity, closure algorithm/roots, reviewer allowlist, and direct guard semantics.
3. Independently review every authorization-required direct source commit in the migration interval. Either leave the production gate red or threshold-sign exact bootstrap ratifications; do not label those commits PR-reviewed.
4. Install the root, policy, ratifications, and executable manifest as protected local files outside the target checkout. On the supported Linux auditor host, install protected, root-owned native executables beneath entirely non-symlinked, non-group/world-writable ancestor hierarchies; provision protected `homePath`, `runtimePath`, and `gitExecPath`; hardlink the three declared builtin helper names to the pinned Git binary; install the separately pinned native `git-remote-https`; bind the exact helper-tree digest; mount `/proc`; and configure rotation/revocation before independently archiving the bytes.
5. Obtain a complete policy-pinned seven-job `main` run, including the cross-image SP1 reproducibility comparator, using the merged paired intro guard; observe the canonical Render deployment; and publish the first v3 receipt in a later evidence-only PR.
6. Invoke `p42-prizes source-release-current-validate` from the independently installed release auditor. The historical archive command remains separate.

Until all six steps are evidenced, v3 current release authority is unavailable by design.
